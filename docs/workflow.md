# 工作流

## 三层读取

1. **L0 导航**：`index.md` 和快照中的来源清单，用于定位。
2. **L1 当前上下文**：`context.md` 与任务卡，保持简短，直接使用人工原文。
3. **L2 详情**：历史知识、决策记录、配置、测试与运行证据，按需读取并登记。

不是为每篇笔记维护三份副本，也不使用模型自动改写人工正本。工具不会生成摘要。

## 一个任务如何完成

1. 人或协调者搜索已有工作；续用原任务 ID，或复制任务示例建立新卡。
2. 人明确目标、范围、验收条件和停止要求；协调者明确负责人及互不重叠的执行范围。
3. Agent 阅读当前原文，capture/read 后保留本会话 SHA。任务卡里引用的资料不会被递归登记；重要依赖用 `--source` 明确加入。
4. 执行者各自输出产物；重要决策前、交接前、修改共享内容前，以自己的 SHA 检查。
5. 来源过期则阅读变化，先判断是否应停止、修改计划或重做；合理处理后再显式刷新。
6. 验证者检查真实产物，协调者记录结论、证据路径、未解决事项和下一负责人。
7. 可复用经验整理成知识笔记；过程日志留在任务产物中。更新任务卡后，需要继续工作的会话重新读取并刷新版本。

任务状态：`planned → active → review → done`；阻塞用 `blocked`，取消/人工关闭用 `cancelled`。
这些是人工协作状态，快照 CLI 不解析或执行它们。侧边栏导出工具读取任务卡 frontmatter 的 `status` 和 `owner`（格式见 sidebar/README.md）；正文不要重复维护另一份状态。它不会领任务、杀进程、发消息或自动签发 PASS。

## 长期记忆最小格式

每条可复用知识保留：结论、适用条件、证据、状态、被哪条新结论替代。
当前规则放短入口，历史结论留原文；不要在一篇越来越长的日志中同时让旧规则和新规则看起来都有效。
人工修改已验证正文后，原回执仍只覆盖原版本，新的结论需要重新核验。

## 并发与恢复

一个任务一个协调者。多个 Agent 可读同一来源，但每个会话的已读 SHA 独立保存；共享快照更新不能让旧会话自动获得新的有效上下文。

`capture` 使用任务目录内 `.context.lock` 防止本工具相互覆盖，临时文件保存后原子替换快照。刷新前旧快照归档为 `context_snapshot.<sha>.json`；来源和快照会被复读。保存后发现来源变化时会报错，已保存的过期快照保留，处理变化后显式刷新即可。

这不阻止检查完成后的编辑，也无法锁住手机或同步软件。写笔记前重查内容，出现冲突保留独立草稿；不要自行选择“最后修改时间较新”的版本覆盖另一方。

快照含绝对根目录，只在本机使用；换机器时不要冒充同一运行环境，建立当地的新快照。快照可证明内容版本是否一致，不能证明谁实际读过、是否理解、是否有授权。

## dsh 会话回执

侧栏只读连接按项目配置读取 Markdown，默认手动刷新；可开启每 60 秒自动刷新（仅页面可见时）。Agent 显式调用 session_context.py read，使用真实宿主会话 ID，将其本次读取的 SHA 保存到仓库 .agent-context/sessions/ 下。每个会话独立检查；另一个会话刷新共享快照不会更新旧回执。

回执只说明工具读取了该版本，不证明模型理解或可信身份。界面刷新不写 Vault、快照或回执；写回前仍须主动 check。没有回执时显示会话未读取。
